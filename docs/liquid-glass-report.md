# 液态玻璃（Liquid Glass）算法探究报告

> 目标：把当前的"模糊亚克力"做成 iOS 26 那种**液态玻璃**观感，**稳定 90 fps**、**CPU < 1%**。
> 本文只做**可行性分析与算法设计**，不含实现。所有数字标了来源：`[实测]` = 本项目里量过的，
> `[推算]` = 按公式算的，`[文献]` = 公开资料/惯例。

---

## 0. 先把硬指标翻译成每帧预算

| 指标 | 含义 | 折算到每帧 |
| --- | --- | --- |
| 90 fps | 每帧 11.11 ms 之内必须完成"取背景 → 变形 → 合成 → 提交" | **11.11 ms GPU+CPU 合计** |
| CPU < 1% | 1 秒内 CPU 累计 ≤ 10 ms（单核口径） | **0.111 ms/帧** |
| 观感 | 边缘透镜 + 镜面高光 + 背景模糊 + 提饱和 + 深度感 | — |

**第一结论：这两条约束把"每帧做 CPU 工作"这条路人彻底堵死了。**
0.11 ms 只够"写几个 uniform + 提交几个 draw call"。任何**逐像素 CPU 计算**、
**GPU→CPU 回读**、**CPU 上传大纹理**都必须从每帧路径里去掉。`[推算]`

参考对照（本项目量到的）：一次全屏 1/6 降采样读回（`Map` + `memcpy`）约 0.3–0.6 ms，
`GDI BitBlt` 抓一帧 40–95 ms。`[实测]` 也就是说：现在这套**每帧做一次**就已经超预算 3–6 倍。

> 注：90 fps 只在 ≥90Hz 的显示器上"真的能看见"。60Hz 屏上窗口最多 60 次呈现，
> 但**帧预算仍按 11.11 ms 设计**，否则高分屏上立刻掉帧。

## 1. iOS 26 的液态玻璃到底做了什么

把它拆成 6 个可独立实现的光学层（按对观感的贡献排序）：

| # | 层 | 物理类比 | 关键参数 | 实现难度 |
| --- | --- | --- | --- | --- |
| 1 | **背景模糊** | 磨砂玻璃 | 高斯 σ ≈ 8–20 px（视尺寸） | ★ |
| 2 | **边缘透镜（折射）** | 厚玻璃边缘的弯月面 | 边缘 12–20% 宽度内有**非线性**位移，中心≈0 | ★★★ |
| 3 | **镜面高光（rim light）** | 边缘的菲涅尔反射 | 边缘 1–3 px 亮线 + 内阴影 | ★★ |
| 4 | **色彩提饱和 / 轻微提亮** | 玻璃本身的色散与增益 | saturation ×1.1–1.3，亮度 +2–4% | ★ |
| 5 | **自适应明暗** | 玻璃会"读"背景亮度决定文字黑白 | 背景平均亮度 → 前景色 | ★ |
| 6 | **动态响应（动效）** | 玻璃有质量感 | 触摸/拖动时高光移动、轻微弹性 | ★★ |

**最容易被忽略、但决定"像不像"的是第 2 层（边缘透镜）**：
iOS 的图标不是"均匀模糊 + 描边"，而是**边缘像凸透镜一样把背景压缩、并向内弯折**，
中心几乎不变形。现在的实现是"整块均匀 bend + 单一边框"，所以看起来是"毛玻璃卡片"，
不是"玻璃块"。`[文献 + 本项目现状对比截图]`

一个能出效果的经验模型（不必真做光线追踪）：

```text
// 每个片元：
d   = 到面板矩形边界的有符号距离（SDF，负=内部）
t   = clamp(1 - |d| / band, 0, 1)          // band ≈ 0.12 * min(w,h)
n   = normalize(grad(d))                    // 指向外侧的二维法线
uv  = uv + n * bend * t^2                   // 二次曲线更接近弯月面
spec = pow(1 - t, 3) * max(0, dot(n, L))    // 边缘高光
col  = blur(uv) * tint + spec * white
```

`t^2` 是"中心几乎不动、越靠边越弯"的关键；用一次幂会变成整体放大（现在的毛病）。

## 2. "窗口背后的桌面"在 Windows 上怎么拿：四条路

这是**整个方案的成本决定项**——因为玻璃必须采样"我背后是什么"。

| 路径 | 拿到什么 | 每帧 CPU | 可控性 | 90fps 可行性 |
| --- | --- | --- | --- | --- |
| **A. DWM 亚克力/Mica**（`DWMWA_SYSTEMBACKDROP_TYPE`） | 系统帮我们模糊好的背景，**拿不到像素** | **0** | ✗ 完全不可控，不能做折射/高光 | ✓ 但不是"液态玻璃" |
| **B. DXGI Desktop Duplication**（当前用的） | 桌面纹理（含自己） | 每次 `AcquireNextFrame` + `Map` 回读 ≈ 0.3–0.6 ms `[实测]` | ✓ 全可控 | ✗ 单次回读就吃掉 3–6 倍预算 |
| **C. Windows.Graphics.Capture (WGC)** | **D3D11 纹理，GPU 内部，零 CPU 拷贝** | ≈ 0.01–0.03 ms（只是拿纹理指针）`[文献]` | ✓ 全可控 | ✓✓ **推荐** |
| D. PrintWindow / BitBlt | 位图 | 40–95 ms `[实测]` | ✓ | ✗ |

**第二结论：必须换成 WGC（路径 C）。** 它把"取背景"从"CPU 搬运"变成"共享一张 GPU 纹理"，
这是同时满足 90fps 与 <1% CPU 的唯一途径。DXGI duplication 之所以慢，是因为它只给
`IDXGIResource`，要么 `Map` 回读（贵），要么再做一次 `CopyResource` 才进得了自己的纹理。

⚠️ 前置条件（要先验证，别写完才发现）：WGC 需要 Win10 1903+，且用
`Direct3D11CaptureFramePool` + `CreateFreeThreaded`；跨进程共享要 `D3D11Texture2D` 同 adapter。
这一条我建议**第一步就写个 30 行的探针**跑通再往下做。

## 3. 目标管线（每帧做什么、在哪做）

```text
┌─ 采集线程（独立，约 30–60Hz，不跟渲染帧率绑）──────────────┐
│  WGC frame → 共享 D3D11 纹理 → 下采样 1/4（GPU）→ 两趟可分离高斯（GPU）│
│  产物：bg_tex（≈ 240×180），双缓冲，原子交换「新帧就绪」标志        │
└───────────────────────────────────────────────────────┘
                       ↓（只传一个纹理句柄 + 3 个 uniform）
┌─ 渲染线程（90Hz，每帧只做 GPU work）──────────────────────┐
│  pass1  折射+模糊采样：uv += n·bend·t²   → col               │
│  pass2  高光/染色：spec + saturation/tint 矩阵              │
│  pass3  面板内容（文字/按键）直接画在最上层                    │
└───────────────────────────────────────────────────────┘
```

关键设计点（都是为了把 CPU 压到 0.11ms 以内）：

1. **采集与渲染解耦**：采集在自己的线程跑 WGC 的事件回调，只更新纹理；渲染线程每帧
   **不做任何等待**，只读"最新可用帧"。窗口 90fps，背景 30–60fps —— 视觉上完全够
   （玻璃是模糊的，背景的低帧率被模糊掩盖）。
2. **零回读**：不做 `Map`、不做"内容有没有变"的 CPU 比较。桌面静止时多跑一次 GPU pass
   的代价（<0.05 ms）远小于一次回读（0.3–0.6 ms）。`[推算]`
3. **所有参数走 uniform**：bend / band / tint / saturation / spec 强度，每帧只写 ≤ 64 字节。
4. **一个 draw call 一层**：把三种玻璃（面板/按键/弹窗）的差异放进 uniform 结构数组，
   不要为每个控件单独起 pass。
5. **不做 CPU 侧模糊**：现在的 `blur_downsample` 是 CPU 两趟 box blur，必须移到 GPU（mip 链或
   compute）。这一项在 1/6 降采样下约 0.2–0.4 ms/次 `[实测]`，每帧做就是 2–4% CPU。

## 4. 帧预算表（目标 vs 现状）

| 阶段 | 现状 `[实测]` | 目标 | 说明 |
| --- | --- | --- | --- |
| 取背景（DXGI + Map 回读） | 0.3–0.6 ms（每 500ms 一次） | **0**（WGC 零拷贝） | 最大的一笔省下来 |
| CPU 模糊（两趟 box） | 0.2–0.4 ms/次 | **0**（移到 GPU） | |
| 内容变化检测（memcmp） | 0.1 ms/次 | 不需要 | WGC 直接给新帧 |
| iced layout+draw（90fps 时） | 3.8 ms/帧 `[实测]` @60Hz | ≤ 6 ms | iced 每帧全量重建，**这是下一个瓶颈** |
| GPU 玻璃 pass | ~0.2 ms | ≤ 1.5 ms | 加 pass 不心疼，GPU 有余量 |
| 合计 CPU | 0.10%（空闲）/ 0.58%（拖动） | **≤ 0.8%** | 已达标，但**靠的是"少干活"**，换成实时背景后要守住 |

⚠️ **最大的隐藏风险不在玻璃，而在 iced**：实测"任意一条消息 ⇒ 整个 view 重建 + layout + draw"，
单帧 3.8 ms。90fps 意味着**每 11.11 ms 就要重建一次**，其中 3.8 ms 是纯 CPU 的 layout+draw。
如果再叠上玻璃的 uniform 更新，很容易顶到 8–9 ms。所以要做 90fps，**必须先给 iced 降重建频率**
（要么只在内容真变时发消息，要么把静态部分做成缓存层）。这一项独立于玻璃算法，建议单列。

## 5. 分三步走（每步都可独立验收）

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| **M1 采集换 WGC** | 写探针确认能拿到 D3D11 纹理；替换 `dupl.rs` 的采集；去掉 `Map` 回读与 CPU 模糊 | 空闲 CPU ≤ 0.5%，背景仍能刷新；截图/录屏正常 |
| **M2 折射模型重写** | 按第 1 节的 `SDF + t² + 边缘高光` 重写 shader，参数化 bend/band | 与 iOS 参考图并排比对（我会出对比图）；GPU ≤ 1.5 ms |
| **M3 交互与打磨** | 自适应明暗、拖动时高光跟随、弹窗与按键的差异化参数 | 拖动 90fps（在 90Hz 屏上实测帧时间） |

## 6. 取舍与风险（先说清，别到实现时才发现）

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| WGC 在部分环境不可用（老系统/远程桌面/虚拟机） | 玻璃退化成纯色 | 保留 "DWM 亚克力" 作为回退档，启动时探测 |
| 实时背景 + 90fps 时 iced 重建成为瓶颈 | 掉帧 | M1 之后先测帧时间分布，再决定是否给 view 做缓存层 |
| 背景帧率 < 窗口帧率 | 快速运动背景上玻璃"糊着一层旧图" | 采集提到 60Hz，并用"运动模糊感"掩盖（iOS 本身也这样） |
| 提饱和过度 | 白底/黑底上色偏 | saturation 上限 1.25，并做亮度自适应 |
| 之前那个"能截图 ↔ 背景真实"的矛盾 | 无解（Windows 限制） | 已在代码里选"能截图"，本报告方案不变 |

## 7. 需要你拍板的两件事

1. **先做 M1（换 WGC）还是先做 M2（改折射模型）？**
   - M1 是性能地基：不做它，M2 做完也只是"一帧好看的图 + 0.5% CPU"。
   - M2 是观感地基：做完能立刻看到"像不像 iOS"，但性能账还没清。
   - 我建议 **M2 先行**（3 天内能看到对比图），因为观感是你真正在意的；M1 紧随其后。
2. **90fps 的验收环境**：你显示器是 90Hz 还是 60/120Hz？60Hz 上"稳定 90 帧"物理上不可能呈现，
   我会改成"帧时间 ≤ 11.1 ms"作为验收口径 —— 这样在任何屏幕上都能验。

## 8. M2 实现记录（2026-10-21）

已落地的三处改动（都在 `liquid.rs` 的片元着色器里）：

| 项 | 旧实现 | M2 |
| --- | --- | --- |
| **法线** | `normalize(像素坐标)` —— 即"从中心指向像素"。宽扁面板上这条方向几乎全是斜的，四条边被斜着推 ⇒ 看起来像整块**放大** | **SDF 有限差分梯度**（4 次 `sd_rr`，e=0.75px）⇒ 法线真正指向最近的边 |
| **环带宽度** | 固定 `u.edge.x`（15/30px），与部件尺寸无关 | `max(thick, 0.085 * min(w,h))` —— 大面板自动变宽 |
| **位移量** | 直接给**归一化 uv**（大件小件弯得一样多） | **像素位移** `t² · strength_px`，再按 `map.xy / win` 折算成图像 uv ⇒ 与抓屏分辨率、部件尺寸都解耦 |
| **高光** | 只看 `uv` 的固定 45° 方向（"画上去"的亮边） | **法线 · 光源** `pow(ndl, 5) · t^2.2` —— 圆角比直边亮、朝光侧亮 |
| **色彩** | 无 | 采样后**提饱和 ×1.18**（玻璃会把背后的颜色喂浓） |

代价：每片元多 8 次 `sd_rr`（abs/max/length，几乎免费）+ 一次亮度点乘。
**实测玻璃模式 CPU：空闲 0.49% / 拖动 0.36%**（都在 1% 以内），CPU 路径完全没动。

**留下的差距**（要在 M1 或后续补）：
1. 合成棋盘快照里边缘已经"弯、中间不动"，但**缺少真机那种"整块薄雾"** ——
   因为测试背景没走模糊管线，而用户的 `模糊强度 = 0` 时真实背景也是清晰的。
   iOS 的观感一半来自**模糊**，建议把玻璃模式的模糊下限抬到 ~0.3。
2. 还没有"动态响应"（拖动时光斑跟随），那是 M3。
3. 采集仍是 DXGI（`Map` 回读），**帧预算的大头在这里**，见第 2 节。
